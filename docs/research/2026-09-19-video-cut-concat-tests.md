# 실측 기록 — 자르기·이어붙이기를 ffmpeg 에 어떻게 맡길 것인가 (2026-09-19)

기획서(`../spec/plan-v0.4.0.md`)의 근거. **전부 lab(Ubuntu 26.04, ffmpeg 8.0.1) 에서 아래 명령으로 재현**했다.
표본은 `sample/Inside Out (2015) (1080p BluRay x265 10bit Tigole).mkv`
(hevc 1920x1080 23.976fps, aac 2트랙, dvd_subtitle 6트랙, 5677.9초, 6.2 Mbps).

## 0. 결론 요약

| # | 확인된 사실 | 설계에 주는 함의 |
|---|---|---|
| A | 무손실 자르기(`-c copy`)는 **0.08초**로 끝나지만 30초 요청이 **32.03초**로 나왔다 (**2.03초 초과**) | 빠르지만 정확하지 않다. "대충 이 대목" 용도로는 충분 |
| B | 이 파일의 키프레임 간격은 **1.0~4.4초로 가변**이다 | A 의 오차는 고정값이 아니다. "오차 ±N초"라고 약속할 수 없다 |
| C | 재인코딩은 **30.072초**로 정확하고, 30초 구간에 **5.68초** 걸렸다 (실시간의 약 5배속) | 정확한 자르기는 실용 범위. 1시간 강의 전체라면 약 11분 |
| D | 같은 소스에서 잘라낸 조각끼리는 concat demuxer 로 **0.11초·무손실** 이어붙는다 | 한 강의 안에서 여러 구간을 뽑아 합치는 것이 주 용도 — 여기는 빠른 길이 있다 |
| E | **코덱이 다른 조각을 `-c copy` 로 이어붙이면 ffmpeg 이 오류 없이 파일을 만들지만 재생이 깨진다** | 가장 위험한 함정. 앱이 **미리 코덱을 대조**해야 한다 (§3) |

## 1. 키프레임 간격 (B)

```bash
V="sample/Inside Out (2015) (1080p BluRay x265 10bit Tigole).mkv"
ffprobe -v error -read_intervals 600%700 -select_streams v:0 -skip_frame nokey \
        -show_entries frame=pts_time -of csv=p=0 "$V"
```

600~700초 구간의 키프레임 시각: 599.974 / 601.434 / 603.228 / 604.187 / 605.855 / 607.148 /
608.608 / 609.984 / 611.569 / 612.612 / 613.780 / 615.406 / 618.117 / 621.496 / 622.539 / 623.873 /
628.169 / 629.921 / 631.130 / 635.552 …

간격이 **1.0초에서 4.4초까지** 널뛴다. x265 인코더가 장면 전환에 맞춰 키프레임을 넣기 때문이다.
→ 무손실 자르기의 오차를 사용자에게 숫자로 약속할 수 없다. "장면 경계로 살짝 밀린다"로만 설명한다.

## 2. 자르기 두 방식 (A·C)

```bash
# 무손실 — 입력 앞에 -ss 를 둬 탐색부터 건너뛴다
ffmpeg -v error -ss 620 -to 650 -i "$V" -map 0:v:0 -map 0:a:0 -c copy cut_copy.mkv

# 정확 — 같은 구간을 다시 인코딩한다
ffmpeg -v error -ss 620 -to 650 -i "$V" -map 0:v:0 -map 0:a:0 \
       -c:v libx264 -preset veryfast -crf 20 -c:a aac cut_enc.mkv
```

| 방식 | 소요 | 결과 길이 (요청 30.0초) | 크기 |
|---|---|---|---|
| `-c copy` | **0.08초** | 32.032초 (**+2.03**) | 22.9 MB |
| 재인코딩 | 5.68초 | **30.072초** | 15.9 MB |

재인코딩 쪽이 **작다** — 원본이 BluRay 리먹스라 비트레이트가 높기 때문이고, 일반적인 결과는 아니다.

> ⚠ `-ss` 를 `-i` **뒤에** 두면 정확해지는 대신 그 지점까지 디코딩하느라 느려진다.
> 위처럼 앞에 두면 ffmpeg 이 키프레임으로 탐색한다 — A 의 오차는 여기서 나온다.

## 3. 이어붙이기 (D·E) — 여기에 함정이 있다

```bash
printf "file '%s'\n" /abs/seg_300.mkv /abs/seg_1200.mkv > list.txt
ffmpeg -v error -f concat -safe 0 -i list.txt -c copy join.mkv
```

**D — 같은 소스 조각(둘 다 hevc)**: 0.11초, 20.603 + 31.280 = 51.883초로 정확히 합쳐졌다.
프레임 pts 를 훑어 0.1초 넘는 점프를 찾으니 끝단에 0.167초 하나뿐 — 경계는 매끈하다.

**E — 코덱이 다른 조각(hevc + h264)**:

```
ffmpeg -v error -f concat -safe 0 -i list2.txt -c copy join_mixed.mkv
#  → 오류 출력 없음. 62.124초짜리 파일이 생긴다. 코덱은 hevc 로 표기된다.

ffmpeg -v error -i join_mixed.mkv -f null -
#  [hevc] Invalid NAL unit size (100663196 > 102013).
#  [hevc] Error splitting the input into NAL units.
```

**ffmpeg 이 막아주지 않는다.** 파일은 만들어지고 길이도 그럴듯한데 두 번째 조각이 디코딩 불가다.
사용자는 내보내기가 성공했다고 믿고 나중에 재생할 때 깨진 것을 발견하게 된다 —
자막 문제 C(한글 큐가 조용히 사라지던 것)와 같은 종류의 **조용한 실패**다.

→ 앱이 조각들의 `codec_name`·`width`·`height`·샘플레이트를 **내보내기 전에 대조**하고,
하나라도 다르면 무손실 경로를 막고 재인코딩으로 넘긴다.
한 영상 안에서 구간을 뽑는 주 용도에서는 항상 같으므로 빠른 길이 유지된다.
