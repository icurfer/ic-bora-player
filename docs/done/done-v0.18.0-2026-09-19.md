## §3 실측이 설계를 바꾼 곳

기획 전에 표본 영상(`sample/`, hevc 1080p 5677초)으로 재현했다. 추정으로 갔으면 틀렸을 지점이 둘 있다.

### 3-1. 무손실 자르기는 "빠른 대신 조금 부정확" 이 아니다

30초를 요청했더니 **32.03초**가 나왔다. 오차 2초는 강의에서 문장 하나가 통째로 더 들어오는 길이다.
게다가 이 파일의 키프레임 간격은 **1.0~4.4초로 가변**이라 "오차 ±N초"라고 약속할 수도 없다.

→ 두 모드를 다 주고, 화면에는 숫자 대신 **"시작·끝이 가까운 장면 경계로 조금 밀린다"** 로 적었다.
정확 모드는 30초에 5.68초(실시간의 약 5배속)라 1시간 강의도 12분이면 끝난다 — 실용 범위였다.

### 3-2. ffmpeg 이 조용히 깨진 파일을 만든다 ⚠ 이번 작업의 핵심

코덱이 다른 조각을 `concat -c copy` 로 이으면:

```
ffmpeg -v error -f concat -safe 0 -i list.txt -c copy join_mixed.mkv
#  → 오류 출력 없음. 62.124초짜리 파일이 생기고 코덱도 hevc 로 표기된다.

ffmpeg -v error -i join_mixed.mkv -f null -
#  [hevc] Invalid NAL unit size (100663196 > 102013).
```

**ffmpeg 이 막아주지 않는다.** 사용자는 내보내기가 성공했다고 믿고 한참 뒤에 발견한다.
자막 인코딩 문제(한글 큐가 조용히 사라지던 것)와 **같은 종류의 실패**다.

→ `probe.can_stream_copy()` 가 내보내기 전에 조각들의 코덱·해상도·샘플레이트를 대조하고,
다르면 멈추고 까닭을 화면에 적는다. 헌법에 "조용한 실패를 만들지 않는다" 한 줄을 더했다.

## §4 곁다리로 잡은 버그 — `p` 키가 죽어 있었다

단축키 표를 정리하다 발견했다. `_on_key` 의 dict 에 `Gdk.KEY_p` 가 두 번 등록돼 있었다:

```python
Gdk.KEY_p: self.toggle_pause,     # 165줄 — dict 리터럴이라 아래에 덮인다
...
Gdk.KEY_p: lambda: self.add_pin(),  # 184줄 — 이것만 살아 있었다
```

핀 기능(v0.2 후반)을 넣을 때 같은 키를 덮어썼고, **README 표에는 둘 다 적혀 있었다.**
`Gdk.KEY_bracketleft/right` 도 같은 모양으로 중복이었다(동작이 같아 무해).

고친 방향: **실제로 동작하던 쪽(핀)을 남기고** 죽은 항목을 지웠다. 동작을 바꾸면 이미 익숙해진
사용자가 혼란스럽다. 대신 README 표를 실제와 맞췄다.

> 배운 것: dict 리터럴의 키 중복은 파이썬이 경고하지 않는다. 단축키가 늘어나면 또 생길 수 있다.

## §5 계측이 먼저 틀린 곳

구현보다 **검증 장치가 먼저 틀린** 경우가 둘 있었다. 둘 다 "실패"로 보였지만 코드는 멀쩡했다.

**5-1. 시나리오가 예외를 삼켜 앱이 영영 돌았다.** `add_clip()` 이 `player.position` 을 불렀는데
그런 속성은 없다(`time_pos` 다). GTK 콜백 안에서 예외가 나자 `self.quit()` 에 도달하지 못해
앱이 끝나지 않았고, 300초 타임아웃으로 죽으면서 **출력이 한 줄도 없었다**. 무엇이 틀렸는지가
아니라 "아무 결과도 없음"으로 보이는 게 문제다.
→ 시나리오의 검사 본문을 `try/except/finally` 로 감싸 무슨 예외였는지 결과에 남기고 반드시 끝낸다.

**5-2. 표본이 작아 취소 테스트가 무의미했다.** C5 는 인코딩 중에 취소하는 검사인데,
320x240 120초는 재인코딩이 **1.1초**라 1.2초 취소 시점엔 이미 끝나 있었다. 파일이 정상 생성됐고
검사는 "부분 파일이 남았다"로 읽어 실패했다 — 원인은 정반대였다.
→ 표본을 640x480 240초(재인코딩 약 4.7초)로 키우고, **취소 알림이 실제로 왔는지**(`"취소됨"`)를
함께 본다. 끝나버린 것을 통과로 세지 않으려는 조건이다.
