# 버전과 릴리스 정책

이 문서는 Codex와 Claude가 함께 따르는 단일 버전 정책이다. AGENTS.md와 CLAUDE.md는
이 정책을 읽도록 지시하며, 버전 관련 결정을 각자 다른 문서에 정의하지 않는다.

## 표준과 프로젝트 선택

오픈소스 전체에 강제되는 단일 버전 체계는 없다. Bora는 [SemVer 2.0.0](https://semver.org/)의
호환성 기준을 사용한다. SemVer는 공개 API를 기준으로 하므로, 이 데스크톱 앱에서는
CLI 옵션, 메모·설정·대화 파일 형식과 보존/이관 동작을 호환성 계약으로 삼는다.
기존 자료를 잃거나 작업 흐름을 끊는 변경은 호환성 검토 대상이다. 내부 함수는 공개 API가 아니다.

- patch: 호환성을 유지하는 오류 수정.
- minor: 호환성을 유지하는 사용자 기능 묶음의 추가. 작업 수나 기획 단계 수가 아니다.
- major: 1.0 이후 호환성 계약을 깨는 변경. 1.0은 핵심 기능과 호환성 계약의 안정화를 선언할 때 정한다.
- 0.x: SemVer상 초기 개발 단계이며 안정성을 보장하지 않는다. Bora에서는 오류 수정은 patch,
  기능 추가 또는 호환성 변경은 minor로 묶되, 호환성 변경과 이관 방법을 변경 내역에 명시한다.

마이너 번호 26 자체는 오류가 아니다. 숫자는 소수점이나 완성률이 아니며 9 뒤에 10이 온다.
코드·문서·기획·세션·커밋마다 버전을 올리던 이전 규칙은 폐기한다.

## 하나의 릴리스, 하나의 버전

`version`은 제품 버전의 원본이다. 허용 형식은 `X.Y.Z`, `X.Y.Z-dev.N`,
`X.Y.Z-alpha.N`, `X.Y.Z-beta.N`, `X.Y.Z-rc.N`이다. 각 숫자는 선행 0이 없는 정수다.
이 제한은 SemVer 전체 문법보다 좁게 정한 프로젝트 규칙이다.

- 개발 중: Unreleased에 변경을 모은다. 같은 개발 주기에는 `version`을 유지하고 커밋으로 구분한다.
- 다음 목표 버전: 직전 배포 이후 변경 묶음을 검토해 한 번 결정한다. 개발 중 목표는 확정 릴리스가 아니다.
- 출시 후보: 범위가 정해지고 기능 검증을 수행한 후보에 rc 번호를 붙인다. 공개한 후보를 고치면 번호를 올린다.
- 정식 배포: 실제 GUI/E2E·필수 단위 검사·패키지 설치 확인 후 버전을 확정한다.
- 작업 보고는 소스/빌드/설치/태그/공개 Release 상태를 각각 구분한다.

개발 빌드는 Git 커밋과 dirty 표시를 추가한다. 예: `0.26.6-dev.1+git.abcdef123456.dirty`.
이는 추적용이며 릴리스가 아니다. 같은 커밋의 서로 다른 dirty 빌드는 동일 식별자를 가질 수 있으므로
공유/배포하지 않는다. 개발 패키지는 로컬 시험용이고 자동 업그레이드 순서를 보장하지 않는다.

## Debian과 Python의 표기

제품의 `1.2.3-rc.1`은 Debian 패키지에서 `1.2.3~rc.1`로 변환한다.
Debian의 `~`는 정식 버전보다 먼저 정렬된다. 문자열이 다르더라도 이 명시된 변환으로 같은 버전이다.
`v1.2.3-rc.1`은 Git 태그이며 `v`는 제품 버전의 일부가 아니다.
Python 패키징 도구는 PEP 440에 따라 `1.2.3rc1`처럼 정규화할 수 있다.
정식 `1.2.3`은 앱·deb·version에서 같고 태그는 `v1.2.3`이다.

근거: [Debian Version 필드](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version),
[Python 버전 명세](https://packaging.python.org/en/latest/specifications/version-specifiers/).

## 개발과 배포 절차

1. 일반 커밋/PR: 코드와 관련 기록을 수정하고 검증한다. 제품 변경은 CHANGELOG Unreleased에 추가한다.
   문서만 수정하면 제품 버전을 바꾸지 않는다. CI는 push/PR에서 실행한다.
2. 로컬 빌드: `bash scripts/build-deb.sh`. 커밋 식별자가 붙은 개발 패키지가 생성된다.
3. 릴리스 준비: 버전 확정, `CHANGELOG.md`에 `## [버전]` 항목과 날짜, 아래 검증 기록을 작성한다.
4. 실제 지원 환경에서 단위·GUI E2E·설치/재실행을 검증한다. 모의 API와 실제 유료 응답은 구분한다.
   GTK 초기화 실패나 처리 함수 직접 호출은 실제 키입력 E2E 통과가 아니다.
5. 커밋·push 후 깨끗한 커밋에 `git tag -a v<버전> -m 'Bora <버전>'`, `git push origin v<버전>`.
6. 태그 workflow는 버전·기록·단위 검사 후 패키지와 SHA256SUMS를 **Draft Release**에 첨부한다.
   실제 화면 검증은 호스팅 CI의 가상 화면 단위 검사로 대체하지 않는다.
7. 릴리스 담당자는 draft의 검증 결과·패키지·후보 표시를 확인하고 공개한다. dev 버전은 릴리스하지 않는다.

`docs/releases/<버전>.md`에는 사용자용 변경 내역과 설치 방법 외에 다음 상태와 구체적인 근거를 적는다.

```text
GUI-E2E: passed
Unit-tests: passed
Platform: Ubuntu 26.04
```

위 표시는 실제 통과했을 때만 작성한다. 사용한 명령/통과 수/실행 환경/스크린샷 경로/설치 결과/
미검증 범위를 본문에 적는다. 자동 검사는 표기의 존재를 검사할 뿐 실제 실행을 증명하지 않는다.
새로운 검증이 실패하면 태그를 만들거나 릴리스를 공개하지 않는다.
`bash scripts/build-deb.sh --release`는 version과 일치하는 태그·깨끗한 트리·기록이 있어야 실행된다.

## 저장소와 배포물

소스·빌드 스크립트·문서만 Git에 보관한다. 새 `.deb` 등 설치 파일은 dist에 생성하되 추적하지 않는다.
정식 설치 파일은 [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
첨부로 제공하고, 일반 개발 CI 산출물은 보존 기간이 있는 Actions artifact로 제공한다.
공개한 태그나 같은 버전의 파일을 교체하지 않는다. 문제가 있으면 새 버전을 낸다.

## 2026-10-09 전환 기록

조회 당시 origin에 태그가 없고 GitHub Releases API 결과도 빈 배열이었다.
그러나 0.26.5까지 `.deb`가 소스 저장소에 공개되고 로컬에도 설치됐으므로 기존 번호는 재사용하지 않는다.
기존 커밋/설치본/CHANGELOG 기록을 보존하며, Git 기록 재작성과 강제 push는 하지 않는다.
현재 트리에서 과거 dist 바이너리는 추적만 해제하고 로컬 파일은 보존한다.

기존 미커밋 `0.26.6`은 E2E 미검증 작업본이었으므로 `0.26.6-dev.1`로 명확히 표시한다.
이 번호는 이미지 전달·단축키 수정 묶음의 임시 개발 목표이며, 정식 다음 버전은 출시 범위 검토 후 결정한다.
예전 기획 파일의 v0.1~v0.10 표기는 문서 이력이며 제품 릴리스와 대응하지 않는다.
새 기획 문서는 제품 버전 대신 주제 이름, 완료 문서는 주제와 날짜를 쓴다.
