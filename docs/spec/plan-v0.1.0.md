## §0 한 줄 정의

**libmpv 를 엔진으로 쓰는 GTK 프론트엔드에, 국내 자막(CP949·SAMI)을 mpv 에 넘기기 전에
"고쳐서" 넘기는 전처리 계층을 붙인 플레이어.** 재생은 만들지 않고, 자막 문제만 정확히 푼다.

## §1 배경 — 왜 만드나

| 관찰 | 근거 |
|---|---|
| VLC 가 Wayland 데스크톱에서 느리다 | VLC 3.x 는 Wayland 네이티브가 아님(XWayland 경유). lab(Ubuntu 26.04 · GNOME Wayland · AMD Vega 내장)에서 체감 |
| 국내 플레이어는 리눅스가 없다 | KMPlayer(판도라TV)·팟플레이어(카카오)·곰플레이어 전부 Windows 전용. `kmplayer` 라는 KDE 패키지는 **동명이인** |
| mpv 계열은 빠르지만 국내 자막에서 깨진다 | §2 실측 |

기존 mpv 프론트엔드(Celluloid·Haruna)는 훌륭하지만 **"자막이 왜 안 나오지"** 를 사용자가 스스로 해결해야 한다.
그 한 가지를 확실히 해결하는 것이 이 프로젝트의 존재 이유다.

## §2 문제 정의 — 실측으로 확정된 것

전부 lab 에서 재현했다(ffmpeg 8.0.1, libuchardet 0.0.8). 상세는 research 문서.

| # | 문제 | 체감 증상 | 원인 위치 |
|---|---|---|---|
| P1 | **CP949 자막을 인코딩 지정 없이 열면 한글 줄이 통째로 버려진다** (깨지는 게 아니다) | "자막이 일부만 나온다", 영어만 나온다 | ffmpeg 디코더가 UTF-8 아닌 줄을 `Invalid data` 로 폐기 |
| P2 | **mpv 의 자동 탐지(uchardet)가 태그 비중 큰 짧은 SAMI 를 `WINDOWS-1252` 로 오탐** | 짧은 영상·예고편 자막이 외계어 | uchardet 가 ASCII 태그에 끌려감. 107 B SAMI → 1252 |
| P3 | **한·영 통합 SAMI 의 언어 클래스(`KRCC`/`ENCC`)가 무시**되어 한 스트림에 섞인다 | 화면에 두 언어가 겹쳐 나옴 | ffmpeg `samidec` 가 `Class` 를 안 본다 |
| P4 | **같은 시각의 SYNC 가 연속되면 앞 큐가 0초** | P3 과 결합하면 한글 큐만 사라짐 | SAMI 큐 길이 = 다음 SYNC 까지, 클래스 구분 없음 |

**핵심 통찰**: P1·P2 는 "인코딩을 맞게 알려주면" 끝나고(`-sub_charenc cp949` 로 정상 확인),
P3·P4 는 "mpv 에 넘기기 전에 SAMI 를 클래스별로 갈라 UTF-8 로 써주면" 끝난다.
→ **문제의 전부가 mpv 바깥의 전처리로 해결 가능**하다. 엔진을 건드릴 필요가 없다.

## §3 제품 정의

### 3-1. 대상 사용자
리눅스 데스크톱(주로 Ubuntu/GNOME)에서 로컬 영상 파일을 국내 자막(`.smi`/`.srt`, CP949 혼재)과 함께 보는 사용자.

### 3-2. 가치 제안
1. **자막이 그냥 나온다** — 인코딩·SAMI 클래스·싱크를 사용자가 만지지 않는다.
2. **빠르다** — libmpv, Wayland 네이티브, 하드웨어 디코딩 기본.
3. **국내 관례를 안다** — `.smi` 자동 로드, 한·영 자막 트랙 선택, 싱크 조절 UI.

### 3-3. 하지 않는 것 (v0.1.0)
- 재생 엔진·코덱·필터 구현 (libmpv/ffmpeg 에 위임)
- 자막 사이트 검색·다운로드 (→ `deferred/`)
- Windows/macOS
- 스트리밍 서비스·DRM
- 플레이리스트 관리·라이브러리(미디어 센터 기능)

A 는 22.04 를 버릴 수 있게 되면 그때 다시 고려한다.

## §5 아키텍처

```
[GTK4 + libadwaita UI]  ── python-mpv (ctypes) ──▶ [libmpv]  ── 렌더 컨텍스트 ──▶ GtkGLArea
        │
        └─▶ [자막 전처리기 (순수 파이썬)]
              ① 인코딩 탐지 2단  → ② SAMI 파서/분리기 → ③ UTF-8 SRT/ASS 임시파일 → mpv --sub-file 로 주입
```

### 5-1. 언어·툴킷 후보

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **Python + PyGObject(GTK4/libadwaita) + python-mpv** | 자막 전처리(문자열·인코딩)에 최적. `ic-crawl` 과 도구 통일. GTK4 렌더 예제 존재 | 시작 속도·배포 크기. 렌더 컨텍스트 연동이 까다로움 | **1순위** |
| C + GTK4 (Celluloid 포크) | 성능·선례 | 자막 전처리를 C 로 쓰는 부담. 포크 유지비 | 2순위 |
| Rust + gtk4-rs + libmpv-rs | 성능·안전 | 학습 곡선, 생태계 성숙도 | 보류 |
| Qt/QML (Haruna 방식) | 기능 풍부 | GNOME 데스크톱과 이질적 | 제외 |

**결정**: Python. 이 프로젝트의 차별점이 전부 **텍스트 처리**이기 때문이다. 렌더 연동 리스크는 §8-3 으로 검증.

### 5-2. 자막 전처리기 — 이 프로젝트의 핵심

**① 인코딩 탐지 (P1·P2 해결)**
```
입력 바이트
 → UTF-8 로 엄격 디코드 성공? ──예──▶ UTF-8 확정
 → 태그·엔티티 제거(<...>, &nbsp; 등) 후 본문만 남김        ← uchardet 오탐의 원인 제거
 → 본문을 uchardet 에 넣어 후보 얻기
 → 후보와 무관하게 cp949 디코드 시도 → 성공 && 한글 음절(가~힣) 비율 ≥ 임계 → CP949 확정
 → 그 외 후보 채택, 전부 실패 시 cp949 폴백 + UI 에 "인코딩 추정" 배지
```
근거: 실측에서 태그 포함 107 B 는 1252 로 오탐, 본문만 27 B 는 UHC 로 정탐.
**태그를 벗기는 것만으로 오탐의 대부분이 사라진다**고 예상 — §8-4 에서 실측으로 확인할 것.

**② SAMI 분리 (P3·P4 해결)**
- `<SYNC Start=N>` / `<P Class=X>` 를 파싱해 **클래스별 트랙**으로 나눈다.
- 큐 길이는 **같은 클래스의 다음 SYNC** 기준으로 계산한다(0초 문제 해소). `&nbsp;` 단독 큐는 "종료" 신호.
- 클래스 이름 → 언어 매핑: `<STYLE>` 의 `lang:` 속성 우선, 없으면 관례(`KRCC`→ko, `ENCC`→en).
- 결과를 트랙별 UTF-8 `.srt`(또는 `.ass`)로 임시 디렉터리에 쓰고 `--sub-file` 로 전부 주입,
  기본 표시는 한국어 트랙.

**③ 비 SAMI(`.srt`/`.ass`)** 는 ① 만 거쳐 UTF-8 로 변환해 넘긴다.

### 5-3. UI 최소 범위 (v0.1.0)
- 파일 열기 / 드래그 앤 드롭 / 명령행 인자
- 재생·정지·탐색·볼륨·전체화면 (libadwaita 헤더바 + 하단 컨트롤)
- **자막 트랙 선택**(전처리기가 만든 트랙 포함), **자막 싱크 조절**(±0.1 s 버튼 + 수치 입력, mpv `sub-delay`)
- 자막 상태 표시: 감지된 인코딩 · "추정" 배지 · 트랙 수
- 같은 폴더의 동명 `.smi`/`.srt` 자동 로드(mpv `sub-auto=fuzzy` 활용, Flatpak 권한 §8-2)

  동봉하면 그 빌드의 라이선스를 따른다. **GPL 계열이 안전**하나 사용자 결정 필요.
