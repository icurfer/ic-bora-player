## §0 한 줄 정의

**libmpv 를 엔진으로 쓰는 GTK 프론트엔드에, 국내 자막(CP949·SAMI)을 mpv 에 넘기기 전에
"고쳐서" 넘기는 전처리 계층을 붙인 플레이어.** 재생은 만들지 않고, 자막 문제만 정확히 푼다.

## §1 배경 — 왜 만드나

| 관찰 | 근거 |
|---|---|
| VLC 가 Wayland 데스크톱에서 느리다 | VLC 3.x 는 Wayland 네이티브가 아님(XWayland 경유). lab(Ubuntu 26.04 · GNOME Wayland · AMD Vega 내장)에서 체감 |
| 국내 플레이어는 리눅스가 없다 | KMPlayer(판도라TV)·팟플레이어(카카오)·곰플레이어 전부 Windows 전용. `kmplayer` 라는 KDE 패키지는 **동명이인** |
| mpv 계열은 빠르지만 국내 자막에서 깨진다 | §2 실측 |

기존 mpv 프론트엔드(Celluloid·Haruna)는 훌륭하지만 **"자막이 왜 안 나오지"** 를 사용자가 스스로 해결해야 한다.
그 한 가지를 확실히 해결하는 것이 이 프로젝트의 존재 이유다.

## §2 문제 정의 — 실측으로 확정된 것

전부 lab 에서 재현했다(ffmpeg 8.0.1, libuchardet 0.0.8). 상세는 research 문서.

**핵심 통찰 (정정판)**
- **P2 는 옵션 하나로 끝난다.** 우리가 판정한 인코딩을 `--sub-codepage=+<enc>` 로 주입하면 mpv 의 탐지를
  완전히 우회한다(§8-6 에서 판정 순서 확인). **자막 파일을 다시 쓸 필요가 없다.**
- **P3·P4 는 한 몸이다.** 한·영 통합 SAMI 를 클래스별로 갈라 주면 둘 다 사라진다(실측 확인).
  단일 언어 SAMI·SRT 는 인코딩만 맞으면 손댈 것이 없다.
- → **문제의 전부가 mpv 바깥의 전처리로 해결 가능**하다는 결론은 유지된다. 다만 **전처리의 양이 예상보다 적다.**

## §3 제품 정의

### 3-1. 대상 사용자
리눅스 데스크톱(주로 Ubuntu/GNOME)에서 로컬 영상 파일을 국내 자막(`.smi`/`.srt`, CP949 혼재)과 함께 보는 사용자.

### 3-2. 가치 제안
1. **자막이 그냥 나온다** — 인코딩·SAMI 클래스·싱크를 사용자가 만지지 않는다.
2. **빠르다** — libmpv, Wayland 네이티브, 하드웨어 디코딩 기본.
3. **국내 관례를 안다** — `.smi` 자동 로드, 한·영 자막 트랙 선택, 싱크 조절 UI.

### 3-3. 하지 않는 것 (v0.1.0)
- 재생 엔진·코덱·필터 구현 (libmpv/ffmpeg 에 위임)
- 자막 사이트 검색·다운로드 (→ `deferred/`)
- Windows/macOS
- 스트리밍 서비스·DRM
- 플레이리스트 관리·라이브러리(미디어 센터 기능)

**기획 당시 권장은 B(Flatpak)** 였다. 코드 분기 없이 "22.04~26.04 전부"를 만족하는 유일한 방법으로 봤기 때문이다.

> **2026-09-13 실측 후 — 판단 재료가 바뀌었다. 둘은 이제 "트레이드오프 하나"로 정리된다.**
>
> - **A 안의 장벽이 셋에서 하나로 줄었다.** libmpv 로딩(8-7)과 렌더 API(8-5)가 해소돼
>   남은 것은 **GTK 4.6 / libadwaita 1.1 범위로 UI 를 짜야 한다**는 제약뿐이다.
> - **B 안에는 없던 장벽이 하나 생겼다.** 동명 자막 자동 로드에 **`--filesystem=host:ro` 가 필수**다(8-2).
>   샌드박스의 이점을 상당 부분 포기하는 선택이고 Flathub 심사에서 지적될 수 있다.
> - Flatpak 의 하드웨어 디코딩은 문제없음이 확인됐다.
>
> **즉 "UI 를 구형 API 로 짜느냐(A)" vs "샌드박스를 넓게 열고 배포 편의를 얻느냐(B)" 의 선택이다.**
> 이 프로젝트의 가치 제안이 **"자막이 그냥 나온다"** 라는 점을 고려하면, 그 기능이 권한 예외에
> 의존하지 않는 A 안이 제품 정체성과 더 맞는다. **남은 확인은 22.04 실기에서의 렌더 하나다.**

## §5 아키텍처

```
[GTK4 + libadwaita UI]  ── python-mpv (ctypes) ──▶ [libmpv]  ── 렌더 컨텍스트 ──▶ GtkGLArea
        │
        └─▶ [자막 전처리기 (순수 파이썬)]
              ① 인코딩 판정 → mpv 에 `--sub-codepage=+<enc>` 로 주입 (파일 재작성 없음)
              ② 한·영 통합 SAMI 만 클래스별로 분리 → UTF-8 SRT 임시파일 → `sub-add` 로 트랙 주입
```

### 5-1. 언어·툴킷 후보

| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| **Python + PyGObject(GTK4/libadwaita) + python-mpv** | 자막 전처리(문자열·인코딩)에 최적. `ic-crawl` 과 도구 통일. GTK4 렌더 예제 존재 | 시작 속도·배포 크기. 렌더 컨텍스트 연동이 까다로움 | **1순위** |
| C + GTK4 (Celluloid 포크) | 성능·선례 | 자막 전처리를 C 로 쓰는 부담. 포크 유지비 | 2순위 |
| Rust + gtk4-rs + libmpv-rs | 성능·안전 | 학습 곡선, 생태계 성숙도 | 보류 |
| Qt/QML (Haruna 방식) | 기능 풍부 | GNOME 데스크톱과 이질적 | 제외 |

**결정**: Python. 이 프로젝트의 차별점이 전부 **텍스트 처리**이기 때문이다. 렌더 연동 리스크는 §8-3 으로 검증.

### 5-2. 자막 전처리기 — 이 프로젝트의 핵심

**① 인코딩 판정 (P2 해결) — §8-4 실측으로 확정, 11/11 통과**
```
입력 바이트
 ① UTF-8 로 엄격 디코드 성공? ──예──▶ UTF-8 확정
 ② 태그·엔티티·SRT 타임코드 제거(바이트 단위) → uchardet 호출
 ③ 결과가 CJK 계열(SHIFT_JIS/EUC-JP/GB18030/BIG5/EUC-KR/UHC)이면 그대로 신뢰
      ← 한글 비율로 뒤집지 않는다. 이 순서가 핵심이다
 ④ Latin 계열·UTF-8 오탐·탐지 실패 → cp949 디코드 후
      '비ASCII 문자 중 한글 음절 비율 ≥ 0.7' 이면 CP949 확정
 ⑤ 못 정하면 cp949 폴백 + UI 에 "인코딩 추정" 배지
 → 판정 결과를 mpv 에 `--sub-codepage=+<enc>` 로 주입한다 (파일을 다시 쓰지 않는다)
```
**기획 시점의 예상이 실측과 달랐던 점** (근거: mpv-playback-path-tests 문서 §2):
- "태그를 벗기면 오탐의 대부분이 사라진다"는 **틀렸다.** 태그 제거는 오탐을 **정답이 아니라 '실패'로** 바꾼다.
  그래도 의미가 있다 — 오탐을 믿으면 모지바케가 확정되지만, 실패로 떨어지면 ④가 돈다.
- **한글 비율만으로는 일본어를 절대 구분할 수 없다.** Shift_JIS 를 cp949 로 디코드하면 한글 비율이 **1.00** 이다.
  그래서 ③(탐지기의 CJK 판정)이 ④(한글 비율)보다 **먼저** 와야 한다.
- 임계 0.7 은 합성 표본 11개 기준이다. **실제 자막 표본이 늘면 재검토할 값이다.**

**② SAMI 분리 (P3·P4 해결) — 프로토타입으로 검증 완료**
- `<SYNC Start=N>` / `<P Class=X>` 를 파싱해 **클래스별 트랙**으로 나눈다.
- 큐 길이는 **같은 클래스의 다음 SYNC** 기준으로 계산한다(0초 문제 해소). `&nbsp;` 단독 큐는 "종료" 신호.
- 클래스 이름 → 언어 매핑: `<STYLE>` 의 `lang:` 속성 우선, 없으면 관례(`KRCC`→ko, `ENCC`→en).
- 결과를 트랙별 UTF-8 `.srt` 로 임시 디렉터리에 쓰고 `sub-add` 로 주입한다.
  **`sub_add(파일, 'select', 제목, 언어코드)` 로 트랙 제목·언어를 지정할 수 있다** → UI 트랙 메뉴에 그대로 쓴다.
- 실측: 한국어 트랙이 기본 선택되고 한·영 겹침과 0초 큐가 모두 사라졌다.
- **적용 대상은 한·영 통합 SAMI 뿐이다.** 단일 클래스 SAMI 는 분리가 필요 없다.

**③ 단일 언어 SAMI·SRT·ASS** 는 ① 만 한다. **파일을 변환하지 않는다** — 인코딩 주입으로 끝난다.

**④ 폴백**: 클래스 분리가 실패한 SAMI 는 `--sub-stretch-durations` 를 켜서 최소한 한글이 보이게 한다.
단 한·영이 겹쳐 보이므로 **기본값으로 삼지 않는다.**

### 5-3. UI 최소 범위 (v0.1.0)
- 파일 열기 / 드래그 앤 드롭 / 명령행 인자
- 재생·정지·탐색·볼륨·전체화면 (libadwaita 헤더바 + 하단 컨트롤)
- **자막 트랙 선택**(전처리기가 만든 트랙 포함), **자막 싱크 조절**(±0.1 s 버튼 + 수치 입력, mpv `sub-delay`)
- 자막 상태 표시: 감지된 인코딩 · "추정" 배지 · 트랙 수
- 같은 폴더의 동명 `.smi`/`.srt` 자동 로드(mpv `sub-auto=fuzzy` 활용).
  **Flatpak 이면 `--filesystem=host:ro` 없이는 불가능하다**(8-2 확정). 권한이 없거나 자막 이름이 다른
  경우를 위해 **"자막 파일 직접 선택" UI 는 어느 배포 방식이든 필요하다.**
  영상과 자막을 함께 선택하면 포털이 둘을 **다른** 디렉터리에 노출하므로, 앱이 인자를 보고 `sub-add` 한다.

## §9 미결

- **라이선스 (8-8)**: 실측으로 구조가 확정됐다 — **우리 라이선스는 "무엇에 링크하느냐"가 정한다.**
  `/usr/share/doc/libmpv2/copyright` 의 서두가 명시한다:

  > mpv 소스는 대부분 GPL-2+ 또는 LGPL-2.1+ 로 배포되지만, **바이너리는 GPL-3+ 인 libsmbclient 에
  > 링크하기 때문에 GPL-3+ 로 배포된다.**

  | 배포 방식 | 링크 대상 | 우리가 고를 수 있는 라이선스 |
  |---|---|---|
  | **A. 호스트 libmpv2 사용** | 우분투 빌드 = **GPL-3+** | 사실상 **GPL-3.0-or-later 고정** |
  | **B. Flatpak 에 libmpv 동봉** | **우리가 빌드 옵션을 정한다.** libsmbclient 를 빼고 LGPL 빌드(`--enable-lgpl`)면 LGPL-2.1+ | GPL-3+ 뿐 아니라 더 느슨한 선택도 가능 |

  → **8-8 은 8-1 에 종속된다.** 다만 어느 쪽을 골라도 **GPL-3.0-or-later 면 충돌이 없고**,
  mpv 생태계 관행(Celluloid·Haruna 모두 GPL)과도 맞는다. **B 를 고르면서 굳이 느슨한 라이선스를
  원하는 경우가 아니면 GPL-3.0-or-later 로 간다.**
